## Proposed compatible producer-first contract — requires root review

Prefer a **separate versioned durable intent API**, not silent reinterpretation of all legacy unkeyed calls or a global provider retry change. Exact route/version/DTO and permission names must be coordinated with Accounting23 before code. Existing v1/Emails wire stays available during an explicit cutover; it remains non-durable and must not be advertised as safe invoice recovery. Existing keyed path REDs are missing-contract requirements to port to the approved durable route, not authorization to change old retry tests.

1. Admit one canonical, purpose-specific UUID before provider effects, scoped to verified issuer/service subject and authorized workflow resource. Accounting must carry reviewed employee/delegation binding, not an arbitrary body-supplied actor. Distinguish invoice from receipt purpose; exact cross-service original intent/key comes from Accounting's durable admission, not a regenerated PDF after lost response.
2. Bind an immutable versioned fingerprint to channel, recipient/reply/CC/BCC, body/subject and ordered attachment bytes/metadata with unambiguous tagged lengths. Persist keyed digest (avoid exposing predictable PII hashes), not mutable caller aliases. Same scoped key/different intent409; same key/same intent reads the admitted record. Canonicalization/null/empty/culture rules must be frozen with literal tests, not inferred from mutable serialization.
3. Durable monotonic state model: `Admitted` (no submission fence yet), `Submitting` (atomic fenced provider attempt), `ProviderAccepted` (validated provider identifier persisted), `RejectedBeforeSubmission` (provably no provider effect), `OutcomeUnknown` (submitted/possible effect but no authoritative result). `ProviderAccepted` must never be labeled delivered. A restart findingSubmitting is uncertain, not safe to resend. Unknown cannot be automatically replayed based on a cache miss, lease expiration, exception category or caller request.
4. Row-locked/CAS complete tuple admission and attempt transition, real configured Npgsql strategy, one guarded submitted-COMMIT attempt, no blind replay after transaction/commit/disposal ambiguity. Zero provider effects when admission/fence/schema readiness acknowledgment is uncertain. Persist result with expected state/generation; stale peers cannot overwrite accepted/unknown. Cancellation before submission has zero provider effects; after submission preserves uncertain authority independently within a bounded token and never assumes a canceled caller means unsent.
5. Permission-checked actor/resource-scoped readback returns only opaque intent UUID, version, state, bounded timestamps and existing provider identifier when appropriate; no recipient/body/file/exception/provider-response disclosure. Cross-actor/resource denial cannot expose row existence. Absence means unknown/unadmitted observation, not authorization to resend a previously uncertain operation. No consumer-owned automatic send reconciliation.
6. Reconciliation can accept independently verified provider/operator evidence under a distinct audited authorization, or remainUnknown. This lane does not invent a Brevo lookup/idempotency promise or implement a resend worker/operator tool. Pending/unknown freezes new email attempts and Accounting/Intranet directs staff to authorized reconciliation.

## 2026-10-01 precise contract addendum — decision proposal, runtime still held

### Storage-owner comparison and selection

Committed Accounting `ae0826156b06c34476e95de8c53dfccfcf5a5972` `InvoiceCreationJournal.cs` stores only the completed workflow response in Redis for30days; `ReceiptOperationJournal.cs` stores completed responses for7days. These observations confirm that none is currently a send receipt.

OptionA is viable only as a different jointly owned design: extend AccountingPG with a notification-specific attempt/result journal, then use a single-attempt stateless Notificationv2 gateway. Accounting would fence before calling the gateway; a crash between that fence and HTTP submission remainsUnknown, and a lost gateway response remainsUnknown even if provider returned an identifier internally. Notification cannot recover that identifier after a restart. Accounting may honestly expose unknown, but cannot satisfy issue26's strict service-local accepted-result/readback expectation without a durable Notification result. A shared database table secretly written by both services is not acceptable ownership.

Select **OptionB: independent Notification-specific durable journal in an existing approved PostgreSQL resource**, no new infrastructure. Accounting retains its workflow admission/employee authorization and observes the Notification receipt; it never treats its Redis cache as Notification authority. The additional store closes Notification's own result-before-HTTP-response crash window, not the provider-send/result-write window. That latter window remainsUnknown without independently verified provider evidence. If no existing approved resource/namespace/grants/capacity are ready, v2 remainsOFF; do not substitute cache, in-memory state or provision infrastructure.

Key scope is `(trustedIssuer, trustedServiceSubject, intentId)`; reusing that ID for another purpose/resource is409, never a second row.

Exact purpose initially `invoice-issued`; resourceType `invoice`; resourceId positive invariant decimal integer string; workflowOperationId nonempty canonical UUID-D. Receipt sends are not implicitly enrolled. Digest is a producer-computed SHA256 over the framing below, lowerhex64; it binds bytes but is not authoritative customer-data proof. Notification computes/persists its own HMAC binding over that digest plus the entire admitted identity. First confirmed insert201; identical replay200; changed tuple/digest409; admission-commit/schema/key uncertainty503 with no capability to execute.

### Immutable framing, HMAC and rotation

Framing version `notification-payload-v1`: exact UTF8 strings, no trim/lowercase/Unicode normalization; each field begins fixed ASCII tag then unsigned64-bit big-endian byte length and bytes. Null uses dedicated `0xff` marker; empty uses present length0, distinct fromnull. Channel uses exact enum name. Fixed order: channel,to,subject,body,replyTo,cc,bcc,attachments. Arrays have present/null marker then uint64 count and ordered samples; CC/BCC order preserved. Each attachment includes exact fileName, contentType (nullable), uint64 content length and bytes. Proposed v2-only admission limits: nonemptyTo and optionalReplyTo/CC/BCC sample at most254UTF8bytes each and valid mailbox; nonemptySubject at most998UTF8bytes; nonemptyBody at most2MiB UTF8; CC/BCC each at most100samples; at most64 nonempty attachments; fileName at most255UTF8bytes; nullable contentType at most127UTF8bytes; aggregate attachment content at most200MiB. Absent optional arrays differ frompresent-empty; null array samples are invalid, not normalized. These limits require producer compatibility fixtures, not silent v1 validation changes. All lengths/counts are checked before allocation. Same null/empty/culture/UTF8 framing shared tests must be literal cross-producer fixtures; do not use default JSON serialization as digest authority.

Notification's `bindingVersion=notification-intent-hmac-v1` HMAC-SHA256 input frames issuer, exact service subject, intentId, purpose, resourceType/id, workflowOperationId, digest version and payload digest with the same tag/length rules. A runtime-only dedicated digest key (not provider/JWT key) with immutable keyID is required. Store keyID/version+HMAC; no key or rawPII. Constant-time comparisons. During rotation, existing records compare using their persisted keyID; new admissions use the current approved key. Old key verification remains available for the entire retained authority horizon. Missing retired/unknown key yields503/unavailable, never new admission or no-send proof. No silent rehash/rebinding and no keyed digest on public readback. A payload SHA can be predictably probed if disclosed; do not log/expose it, persist only HMAC binding plus necessary versioned metadata after admission. Execute recomputes SHA then HMAC and compares to stored binding; plaintext SHA need not be stored.

### CAS graph, uncertainty and retention

Allowed transitions: `Admitted→Submitting` under exact row/version fence; `Submitting→ProviderAccepted` only with validated provider ID and acknowledged durable result; `Submitting→OutcomeUnknown` after possible provider effect/result ambiguity. A staleSubmitting observed after process loss is readback as uncertain and may CAS toOutcomeUnknown; it never returnsAdmitted. `Admitted→RejectedBeforeSubmission` is allowed only for a demonstrably effect-free definitive validation rejection after admission, not any HTTP provider rejection. TerminalProviderAccepted/OutcomeUnknown/RejectedBeforeSubmission do not silently mutate. Any eventual operator/provider reconciliation is a separate audited capability/state transition, absent from this implementation proposal.

Admit/fence transactions use the actual configured execution strategy with exactly one guarded transaction attempt; pre/postCOMMIT/disposal ambiguity is fixed-message typedunknown, no retry/upsert escape and zero provider action until a confirmed fence. Result persistence runs bounded independently of an aborted request but cannot overwrite a committed peer. Result-COMMITlostACK requires safe re-observation: confirmed same accepted receipt may be returned; unavailable/ambiguous observation503 preserves existing fence. A failure to markUnknown does not destroySubmitting authority. No background send/redelivery worker. Intent status404, cache miss, key expiry, timeout, crash or canceled caller never enables another submission.

Unresolved/Submitting/OutcomeUnknown authority has **no automatic TTL or deletion**. ProviderAccepted/RejectedBeforeSubmission retain non-PII tuple/HMAC tombstones at least the coordinated producer replay horizon (invoice current30days; receipt7days not yet enrolled), and until the owner approves an archival/retention policy preserving collision protection. No automatic deletion is implemented in the first slice; retention/privacy review is a cutover prerequisite, not permission for infinite rawPII retention. No raw recipient/body/PDF/customer/name is persisted. Resource IDs and verified subjects are minimal operational identifiers and remain protected access-controlled data, not anonymized public data.
